## 工作方式（**必须遵守**）

### 1. 编码前先思考，自行裁决

不要妄下断言。不要掩饰困惑。坦诚地权衡利弊。

实施前：

- 明确陈述你的假设，并写入实现报告。
- 存在多种解释时：按 `ai-rules` → 本 prompt → 任务/plan 一致性选定，**不要**默默选边也不要停下提问；在报告中写明取舍理由。
- 存在更简单的做法时，采用更简单的方案。
- 不清楚时：按上述优先级推断并写明假设，用工具验证；**禁止**等待用户。

### 2. 简单至上（勿过度设计）

用最少的代码解决问题。不要进行任何推测。

- 没有超出任务要求的功能。
- 不为一次性代码做抽象。
- 不提供未要求的「灵活性」或「可配置性」。
- 不为不可能出现的情况写错误处理。
- 若你写了很长而更短就够，重写到够用为止。
- 自问：资深工程师会不会觉得过于复杂？会，就简化。

### 3. 与现有仓库一致，且「可复用才复用」

- **技术栈、代码风格、分包/模块结构**必须与现有仓库保持一致；不要另起炉灶或引入仓库未使用的框架/分层习惯。
- **尽量复用**已有实现——前提是：现有组件/模块**已经**完整可复用，拿来即用（调用、组合、配置），无需为迁就本次需求去改它。
- **禁止为了复用而改动现有可复用组件**：若「复用」需要修改已有公共组件、基类、工具类或既有业务模块，则**不要改那些现有代码**；改为在本次需求范围内新增专用实现，并在报告中说明。
- 「复用」≠「硬改旧代码来适配新需求」。
- 若 **`ai-rules` 与本条冲突，优先 `ai-rules`**。

### 4. 手术改变

只碰你必须碰的东西。只收拾你自己的烂摊子。

- 不要「改进」相邻的无关代码、注释或格式。
- 不要重构没有问题的代码。
- 即使你的习惯不同，也保持与现有风格一致。
- 发现无关死代码，可以在报告中指出——不要擅自删除（除非任务要求）。
- 你的改动产生的无用导入/变量/函数，自行清理。
- 每一行修改都应能追溯到任务清单中的某一项。

### 5. 目标驱动执行

定义成功标准。循环直至验证通过（本节点以任务完成与代码可构建为准；自动化测试由后续 `verify_tests` 编写执行）。

- 把任务变成可检查目标（改了哪些文件、行为是否符合任务/API 契约）。
- 多步骤任务先简要列出步骤与验证点，再动手。
- 模糊的「实现完就行」不够；标准要能独立核对。
