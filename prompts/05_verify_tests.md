## 写作与提问语言（**全程必须遵守**）

- **用人话写，别像 AI**：测试报告要像资深工程师写给同事看的内部技术文档，直白、具体、不绕。**禁止** AI 腔：堆砌「综上所述」「值得一提的是」「首先…其次…最后」、过度对仗排比、空洞套话、emoji 装饰、无意义的礼貌用语。该用要点用要点，该一段说清就一段。
- **提问前先写清现状（AS-IS）**：用例/预期不清需向用户提问时，若涉及现状，必须先用直白话把**当前现状**写进 `as_is` 字段——现在是怎么做的、现有逻辑/数据/交互是什么样——再在 `question` 提出问题。没有现状（全新增）则 `as_is` 留空，直接问。

## 四阶段任务（必须按序完成，允许阶段内循环）

### 阶段 1：按 input 完成测试编写

1. 做 AS IS 判断：本项目要跑哪些层（单测 / API / E2E）。
2. 从报告找到附件路径并打开用例正文；对照附件在项目既有栈中**编写/补全**可执行验证（编号与附件一致、可追溯）。
3. 本阶段以「验证手段就绪、可执行」为完成标准，尚未要求全部绿。

### 阶段 2：验证循环 — 直到全部应执行用例通过

循环执行，**禁止**失败后只打标就结束：

1. 运行本阶段应执行的全部测试。
2. 若出现失败 / 异常：
   - **先归因**：是**测试编写问题**（断言错、夹具错、环境/路径错、用例理解错）还是**实现问题**（生产代码不符合验收）？
   - 测试问题 → 修测试（或修正错误理解后与用户确认口径）。
   - 实现问题 → **修生产代码**（手术改变，仅改与失败用例相关的实现），再重跑。
   - 归因不清 → **先问用户**再改。提问时用自然语言完整描述失败现象与归因疑点，禁止 `d2`/`m0` 等代号指代模块/用例/配置（须写全名 + 一句话说明），并给出倾向归因及推荐原因。
3. 重复直至：应执行用例全部 `pass`；`skip` 仅保留 AS IS / rule 合法跳过项。
4. 在报告中记录关键失败轮次的归因与修复摘要（不必逐条堆日志）。

**最终目的**：可执行测试全部通过，而不是「跑一遍记 fail」。

### 阶段 3：置信度打分与挑刺（发布视角）

以 **QA 负责人**身份，在**全部应执行测试已通过**的前提下，评估「现有测试覆盖是否有信心直接上线」，给出 **0～1** 的置信度（保留两位小数即可）。

主要依据（结合仓库与报告如实写）：

- 测试覆盖是否覆盖需求验收与关键路径（含失败/边界）
- 数据真实性（是否贴近真实业务数据 / 是否过度 mock）
- 外部依赖（真实联调 vs mock；不稳定依赖是否暴露）
- 项目 AS IS 导致的 skip 是否留下上线盲区
- 其它：`ai-rules` 要求、实现报告中的已知限制等

阈值：**置信度 < 0.8** 时进入阶段 4；≥ 0.8 可进入阶段 5 收尾（仍须写清理由）。

### 阶段 4：补测循环 — 抬升置信度

当置信度 < 0.8：

1. 列出**可补且本节点能做**的缺口（新用例/断言/夹具/关键路径），优先高风险。
2. 补测后回到**阶段 2** 跑绿，再重新打分。
3. 重复直至：
   - 置信度 ≥ 0.8，或
   - **本节点能力内已无法再提升**（例如缺真实环境、缺外部系统、AS IS 无 E2E 栈且 rule 禁止自造）——须在报告写明「已做尽 / 未做尽及阻塞原因」。

补测仍须遵守 AS IS：不能为抬分引入项目没有的测试技术栈。

### 阶段 5：定稿报告

写入 `{{output_path}}`，**禁止**只写概述。必须包含：

1. 执行环境与命令（含 AS IS：用了哪些既有验证手段、哪些用例 skip 及依据）
2. 验证循环摘要（失败归因：测试 vs 实现，及修复要点）
3. 用例追溯表（附件编号 ↔ 执行方式 / 命令或脚本）
4. 置信度评估：
   - **最终置信度**（0～1）
   - **是否达到 0.8**
   - **评分依据**（覆盖、数据真实性、外部依赖等）
   - **补测循环做了什么**；若仍 < 0.8，说明已做尽事项与残余风险
5. 问题与建议
6. 用例结果表（正文最后；编号与附件一致）：

```markdown
| 用例编号 | 结果 |
|----------|------|
| TC-01 | pass |
| TC-02 | skip |
```

结果列只允许 `pass` / `skip` / `fail` / `blocked`。  
**收尾前**：应执行项不得残留 `fail`（除非用户明确授权放弃修复并记入报告——默认不允许）。

报告正文与结果表写完后，在同一文件末尾写入定稿标记（引擎据此自动进入下一节点；未写或仍为 `pending` 时本节点不结束）：

```yaml test_report_approval
status: approved
confirmed_at: "<ISO8601>"
user_note: "阶段 5 定稿完成"
```

- 阶段 1～4 进行中、报告未定稿时：不要写该块，或保持 `status: pending`
- 阶段 5 收尾完成：必须写成 `approved`；写完即表示本节点完成，**不要**再等人确认「继续」
- `test_cases_approval`（用例报告里）与此无关：用例未经 QA review 只在「问题与建议」标注，**不**阻塞本节点定稿
