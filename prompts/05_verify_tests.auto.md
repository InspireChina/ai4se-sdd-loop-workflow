## 写作语言（**全程必须遵守**）

**用人话写，别像 AI**：测试报告要像资深工程师写给同事看的内部技术文档，直白、具体、不绕。**禁止** AI 腔：堆砌「综上所述」「值得一提的是」「首先…其次…最后」、过度对仗排比、空洞套话、emoji 装饰、无意义的礼貌用语。该用要点用要点，该一段说清就一段。用例歧义自决时，若涉及现状先写进 `as_is` 字段再给结论。

## 工作方式（**必须遵守**）

### 1. 用例歧义自行裁决

**用例 review 状态软提示**：若 `02-test-cases.md` 的 `test_cases_approval` 仍为 `pending`（QA 尚未异步 review），本节点**不阻塞**，继续执行测试，但须在最终报告「问题与建议」章节标注「测试用例未经 QA review，结果供参考」。

### 2. 简单至上 / 手术改变 / 可复用才复用

沿用项目既有测试栈；禁止为复用改公共基座；若 **`ai-rules` 冲突，优先 `ai-rules`**。

### 3. 测试范围：项目 AS IS + 扩展 rule

**视项目现有能力与 `ai-rules` 而定，禁止自行发明栈。**

1. **单元**：按既有单测栈编写并执行。

3. **E2E**：已集成则按项目方式跑；未集成且 rule 未要求 → **skip**。

「全部通过」= 应执行用例均为 `pass`；合法 `skip` 不算失败。勿因无人值守硬跑项目不具备的能力。

## 四阶段任务（必须按序；阶段内自行 loop）

### 阶段 1：按 input 完成测试编写

AS IS 判定要跑的层 → 对照 `02-test-cases.md` 在既有栈中编写/补全测试（可追溯编号）。

### 阶段 2：验证循环 — 直到全部应执行用例通过

**禁止**失败后只打标结束。循环：

1. 跑应执行的全部测试。
2. 失败时**强制归因**并修复：
   - **测试编写问题** → 修测试；
   - **实现问题** → 修相关生产代码（手术改变）；
   - 归因按证据选择并写明（日志、断言、代码路径）；勿停下来等人。
3. 重跑直至应执行项全部 `pass`。

### 阶段 3：置信度打分与挑刺

全部应执行测试通过后，以 QA 负责人视角给出 **0～1** 上线置信度。依据至少覆盖：

- 测试覆盖（验收与关键路径/边界）
- 数据真实性
- 外部依赖（真实 vs mock、盲区）
- AS IS skip 带来的上线风险
- `ai-rules` / 实现报告中的已知限制

阈值：**置信度 < 0.8** → 进入阶段 4；否则进入阶段 5（仍须写清理由）。

### 阶段 4：补测循环 — 抬升置信度

置信度 < 0.8 时：列出本节点**能做**的补测 → 补完回到阶段 2 跑绿 → 重新打分。  
重复直至 ≥ 0.8，或**能力内已做尽**（缺环境/外部系统/AS IS 无栈等）——报告写明已做尽与残余风险。  
补测仍遵守 AS IS，禁止为抬分引入新栈。

### 阶段 5：定稿报告

写入 `{{output_path}}`，须含：

1. 执行环境与 AS IS 判断
2. 验证循环摘要（测试 vs 实现归因与修复）
3. 用例追溯表与分层结果
4. **最终置信度（0～1）**、是否达 0.8、评分依据、补测过程；若仍 < 0.8 写明已做尽与残余风险
5. 问题与建议
6. 用例结果表（正文最后）；应执行项不得残留 `fail`

```markdown
| 用例编号 | 结果 |
|----------|------|
| TC-UNIT-01 | pass |
| TC-API-01 | skip |
```

结果列只允许 `pass` / `skip` / `fail` / `blocked`。
