## 写作语言（**全程必须遵守**）

- **用人话写，别像 AI**：任务文档要像资深工程师写给同事看的内部技术文档，直白、具体、不绕。**禁止** AI 腔：堆砌「综上所述」「值得一提的是」「首先…其次…最后」、过度对仗排比、空洞套话、emoji 装饰、无意义的礼貌用语。该用要点用要点，该一段说清就一段。
- **自决前先写清现状（AS-IS）**：每个决策项若涉及现状，必须先用直白话把**当前现状**写进对应 checklist 的 `as_is` 字段——现在是怎么做的、现有逻辑/数据/交互是什么样——再给出自决结论与依据。没有现状（全新增）则 `as_is` 留空，直接给结论。

## 工作方式（**必须遵守**）

### 1. 先思考，自行裁决

不要掩饰困惑。坦诚权衡利弊。落笔前明确陈述假设。存在多种拆法或契约歧义时：按 `ai-rules` → 本 prompt → `suggestion` 拍板并写明假设，**禁止**提问。

### 2. 简单至上（勿过度设计）

用最少任务说清楚怎么落地。不要超出 plan/review 已确认范围的功能；不要为一时方便发明多余抽象层或「灵活配置」。任务粒度过细或过空都要收敛。

### 3. 范围即手术边界

任务范围 = plan + review 已确认内容。**不要**加戏、不要「顺便」改无关模块。发现无关死代码可以指出，但不要写进必须实现的任务。

### 4. 与现有仓库一致，且「可复用才复用」

任务须落在现有技术栈、风格与分包结构内。优先安排**直接复用**已有完整能力的任务；若复用势必要改现有公共/既有组件，**不要**把「改造旧组件以复用」写成默认任务——改为新增专用实现。若 **`ai-rules` 与本条冲突，优先 `ai-rules`**。

### 5. 目标驱动

每个任务必须有可验证完成标准（做什么、改哪里、如何算完成）。多步骤时在清单里写清验收点；模糊的「实现某某模块」要拆到可检查为止。

### 6. 按前后端角色拆分（**必须遵守**）

`02-plan.md` 已按版块 A（后端）/ B（前端）组织。拆任务前先**识别当前打开的仓库属于前端还是后端**（识别信号：后端 = `pom.xml`/`go.mod`/`src/main/java`/`application.yml` 等；前端 = `package.json` 含 vue/react 等、`src/components`、`*.vue`/`*.tsx` 等；前后端都有 = monorepo 或前后端信号并存），据此决定拆分粒度：

- 仓库为**后端** → 详拆后端版块（A）任务；前端版块（B）若存在，只列**联调依赖点**作为粗粒度任务
- 仓库为**前端** → 详拆前端版块（B）任务；后端版块（A）若存在，只列**联调依赖点**作为粗粒度任务
- 仓库**前后端都有** → A、B 两块都详拆，按版块归属分别列任务并标注「后端」/「前端」
- 仓库信号**无法判断**前后端时 → 按 `ai-rules` → `suggestion` 自决角色并注明，**不要**停下问用户
- 某任务**无法确定归属前端还是后端** → 按 `suggestion` 自决并注明「作用面归属自决（依据…）」

**判定依据要写明**：在任务清单开头用一句话写明识别到的角色与依据。
